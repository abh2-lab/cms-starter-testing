# AI theme authoring

This is the developer manual for the **AI Theme-Authoring Kit** — the tooling that
turns a **mock design into a working theme** (blocks, templates, parts, sample
content), driven by an AI assistant *or* by hand. For *what* blocks and templates
are, read [Blocks](?doc=blocks) and [Page templates](?doc=page-templates) first;
this guide is about **building** them quickly and safely.

## What the kit gives you

Four layers over the block/template system you already know:

| Layer | What it is | You run |
| --- | --- | --- |
| **Knowledge** | `AGENTS.md` at the repo root — the assistant's onboarding guide (the loop, commands, hard rules). | *(an assistant reads it)* |
| **Generation** | `gen:block` / `gen:template` — scaffold both halves of a block (server loader + Vue renderer) and wire both registries. | `pnpm gen:block`, `pnpm gen:template` |
| **Gate** | `verify:theme` — validates metas, registry coherence, the build, and fixture bindings. | `pnpm verify:theme` |
| **Fence** | A DB-free import lint, a diff-scope guard, and a build-time gate, so broken or out-of-scope code can't reach the live site. | `pnpm lint`, `pnpm check:theme-scope` |

## Authoring runs in hybrid dev — never on the live site

Author themes in **hybrid dev** on your machine — backing services in Docker, the
apps from source. At runtime the theme is **baked into the Docker images at build
time** and served on Coolify, so there is nothing to edit on a live box.

```bash
pnpm install
pnpm dev:services      # backing services only: Postgres, Redis (Dragonfly), Meili, MinIO
pnpm dev               # apps from source — admin :5173, web :3001, api :3000
```

> **Don't author on the live container.** `gen`, `verify`, and the preview loop run
> only in hybrid dev. The deployed image is immutable theme code — to change it you
> re-author here, re-verify, rebuild the image, and redeploy.

## The loop

```text
mock design
  │  decompose into blocks + a template/part            (judgment)
  ▼
pnpm gen:block / gen:template                            (scaffolds both halves + both registries)
  │  fill in load() (data) + the .vue (markup)           (you / the assistant)
  ▼
author fixtures → apps/api/fixtures/<name>/              (sample content to bind to)
  ▼
pnpm verify:theme  ◄──── loop until GREEN ────┐          (structure + content checks)
  │                                            │  fix what it reports
  ▼                                            │
pnpm dev → preview, compare to the mock ───────┘
  ▼
★ HUMAN QA ★   visual fidelity, runtime render, a11y / responsive
  ▼
commit → build images (gate runs) → deploy → seed content
```

The one manual checkpoint is **human QA after the preview renders** — `verify:theme`
green proves the structure is sound, not that it looks right (see **Verifying** below).

## Prompting your AI assistant

You don't run the generators yourself — you hand your assistant a prompt and it runs
the loop. The trick is the **first line: tell it to read `AGENTS.md`**. That one line
routes it to the command list, the hard rules, and the loop, so it self-onboards — it
discovers *where the knowledge is* and *how to proceed* without you spelling it out.

Lift these directly (swap in your own mock paths):

**Build a whole theme from a mock**

```text
Read AGENTS.md at the repo root, then build a theme from ./mocks/home.html.
Decompose it into blocks plus a page template, scaffold each with `pnpm gen:block`
and `pnpm gen:template`, fill in every load() and .vue, author seed fixtures under
apps/api/fixtures/, and loop on `pnpm verify:theme` until it is green. Then run
`pnpm dev`, screenshot the result, and stop for my review. Stay inside the theme
surface — do not touch the API or the database.
```

**Create a single block**

```text
Read AGENTS.md. Create a standalone block `author-card` that matches
./mocks/author-card.png: run `pnpm gen:block`, fill in load() and the .vue, then
run `pnpm verify:theme`.
```

**Create a template or part**

```text
Read AGENTS.md. Build a `header` part from ./mocks/header.html: generate the blocks
it needs with `pnpm gen:block`, then `pnpm gen:template` for the part, wire it, and
run `pnpm verify:theme`.
```

> **The first line is the whole trick.** "Read AGENTS.md" makes the assistant discover
> the tools and rules itself, so your prompt stays short. The starter zip also ships
> `CLAUDE.md`, `.windsurfrules`, and `.cursor/rules/ai-authoring.md` (generated by
> `pnpm export:starter`), each pointing at `AGENTS.md` — so assistants that auto-read
> those files land on the kit even from a bare "build me a theme from this mock".

## Generating a block — gen:block

`gen:block` automates the five manual steps from [Adding a block](?doc=blocks) so the
two halves can never drift apart. By hand those steps are:

1. **Server meta + loader** — new file `packages/blocks/src/blocks/<key>.ts`.
2. **Register it** — import + a `blockRegistry` entry in `packages/blocks/src/registry.ts`.
3. **Render component** — new file `…/app/components/blocks/Block<Name>.vue`.
4. **Register the component** — import it under the **same key** in `…/composables/useBlockRegistry.ts`.
5. **Rebuild + restart** — `pnpm --filter @cms/blocks build`, restart API + admin.

One command does all five (and keeps the key identical across both registries):

```bash
pnpm gen:block --key author-card --kind standalone --label "Author Card" --category lead
```

For anything with fields or options, pass a JSON spec instead:

```bash
pnpm gen:block --spec ./author-card.json
```

```json
{
  "key": "author-card",
  "kind": "standalone",
  "label": "Author Card",
  "category": "lead",
  "icon": "user",
  "lazy": false,
  "fields":  [{ "key": "blurb", "label": "Blurb", "type": "short_text" }],
  "options": [{ "key": "author_slug", "label": "Author", "type": "content_slug", "required": true }]
}
```

**Fields vs options:** `fields` are editor-typed copy (titles, labels — overridable
per page); `options` are data bindings (which story, which category). Field/option
`type` is one of `short_text`, `long_text`, `number`, `boolean`, `url`, `select`
(needs `options: [...]`), `content_slug`, `content_type_slug`, `category_slug`,
`custom_field`, `kv_list`.

**The four kinds** (the box model — see [Blocks](?doc=blocks) for the full story):

| Kind | `load()` returns | the `.vue` renders | reads | sets |
| --- | --- | --- | --- | --- |
| `standalone` | its own data object | the data | — | — |
| `field` | a projection of the current post | the value | `ctx.box` | — |
| `container` | `null` | `<slot/>` (children) | passes the box through | — |
| `box` | `null` (+ `resolveBoxes()`) | `<slot/>` per item | — | `ctx.box` for descendants |

`gen` writes compiling `TODO(human)` stubs for `load()` and the `.vue` — fill them in,
then run `pnpm verify:theme` (it rebuilds `@cms/blocks` for you). Use `--lazy` for
tiptap-heavy blocks (rich-text bodies) to keep them off non-article bundles. Re-running
`gen:block` for the same key is **idempotent**: it updates the registries in place and
skips files you've already edited.

## Generating a template or part — gen:template

`gen:template` does the same for the [page-template recipe](?doc=page-templates) — it
writes the `TemplateMeta` file and registers it. The `role` decides the target:

| `role` | Target | Notes |
| --- | --- | --- |
| *(none)* | `templates/<key>.ts` → the admin "+ New Page" set | a plain page template |
| `header` / `footer` / `sidebar` | `parts/<key>.ts` → the part registry | site chrome |
| `single` / `archive` / `search` / `404` / … | a role-resolved template | leaves a `TODO(human)` in `resolve-template.ts` — selection logic is wired by a developer |

```bash
pnpm gen:template --spec ./home.json
```

Every `block_key` in the template must already exist — generate the blocks first. New
templates get `version: 1`; bump it later when you change a template's structure so
admins who customized it see an "update available" badge (see
[The theme engine](?doc=theme-engine)).

## Authoring by hand

You don't have to use `gen`. The fully manual recipes are
[Adding a block](?doc=blocks) and [Page templates](?doc=page-templates); `gen` just
scaffolds those steps and wires the registries so the keys can't drift. Whichever way
you author — generated or by hand — run `pnpm verify:theme` before you commit. It
catches the same mistakes either way.

## Sample content — fixtures

A generated template renders **empty** until there's content to bind to. Author sample
content as JSON fixtures under `apps/api/fixtures/<name>/` (copy the shape of the
existing `example/`, `decode/`, `sample-cpt/` sets — `content-types.json`,
`taxonomies.json`, `posts.json`, `pages.json`). `verify:theme` checks that every
content type / category / slug your blocks bind to actually exists in those fixtures,
so a template that passes structure but would render blank is caught before you ship.

Seed a set into a running database:

```bash
pnpm --filter @cms/api seed:fixtures -- <name> --tenant=<slug>
```

The seeder is idempotent and tenant-scoped — re-running it is safe.

## Verifying — verify:theme

`pnpm verify:theme` is the gate you loop on. It runs two scopes:

| Scope | Checks |
| --- | --- |
| `verify:theme:structure` | zod-validates every block/template/part meta; **registry coherence** (every server key has a matching Vue component, and vice-versa); the `@cms/blocks` build; a render-smoke that runs each `load()` against a stub context |
| `verify:theme:content` | the fixture schemas, and the **block↔fixture binding** (the bound content types / terms / slugs exist) |

Add `--json` for machine-readable output — that's what the assistant loops on.

> **Green proves structure, not pixels.** `verify:theme` confirms keys match, types
> align, loaders don't throw, and bound content exists. It does **not** mount the
> `.vue` — a component that crashes at render can still pass. Always preview in hybrid
> (`pnpm dev`) and do a human QA pass before shipping.

## Guardrails

Three runnable guardrails keep authored code safe — there is no mandatory branch or
PR flow:

- **Blocks stay DB-free.** A block imports nothing from `@cms/db` or the API; it only
  uses the `ctx` it's handed. `pnpm lint` enforces this.
- **Diff-scope guard.** `pnpm check:theme-scope` fails if a change touches anything
  outside the theme surface (the block/template/part files and their registries, the
  theme's `components/blocks` + `useBlockRegistry.ts`, and `apps/api/fixtures`).
- **Build-time gate.** The web Docker image runs `verify:theme:structure` during its
  build, so broken theme code fails the image build and can never reach the live site.

## Deploy & seed

The path from an authored theme to a live site:

1. Author in hybrid, `verify:theme` green, human QA.
2. **Commit** the theme code (it's part of the repo).
3. **Build the Docker images** — the web image re-runs `verify:theme:structure`; a
   broken theme fails the build.
4. **Deploy to Coolify** — `db-migrate` runs, the setup wizard creates the tenant +
   super-admin.
5. **Seed the starter content** with a one-shot against the deployed api:

```bash
docker compose run --rm api \
  pnpm --filter @cms/api seed:fixtures -- <name> --tenant=<PUBLIC_TENANT_SLUG>
```

Theme **code** ships inside the image; sample **content** is seeded into the deployed
database after first boot.

## How this fits with the rest

- `gen:block` / `gen:template` automate the manual recipes in
  [Blocks](?doc=blocks) and [Page templates](?doc=page-templates).
- The runtime override engine in [The theme engine](?doc=theme-engine) is
  complementary: once your generated templates/parts ship, admins customize them at
  runtime with **no code change**. Generated templates are override-compatible by
  construction (correct `role`, `version: 1`).
- For CSS tokens, fonts, the dev workflow, and the file layout of the theme itself,
  see [Managing the theme](?doc=managing-the-theme).

## Gotchas

- **Rebuild `@cms/blocks` after editing a loader** — the admin and API read the built
  `dist/`, not source. `verify:theme` rebuilds it for you; if you skip verify, run
  `pnpm --filter @cms/blocks build` yourself.
- **Key mismatch → blank render** — the server `meta.key` and the Vue registry key
  must be identical. `gen` keeps them aligned; `verify:theme`'s coherence check catches
  drift.
- **Field / container / box blocks aren't previewable on their own** — the block-gallery
  preview returns **422** for non-standalone kinds. Preview them by placing them in a
  template.
- **Never `prettier --write`** — this repo has no Prettier config; ESLint is the only
  formatter and gate. `gen` emits eslint-clean, single-quoted code.
- **Never author on the live container** — authoring is a hybrid-dev, build-time
  activity (see the boundary above).
